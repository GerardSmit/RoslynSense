# Where RoslynSense stands against Rider and Visual Studio

A measured audit, not an impression. 1,093 Rider/Visual Studio capabilities were catalogued from
JetBrains and Microsoft primary documentation across 25 domains, then every one of them was checked
against this repository before being called a gap. What Rider and VS actually provide is in
[ide-capability-catalog.md](ide-capability-catalog.md); the evidence behind each line below is in
[ide-gap-register.md](ide-gap-register.md).

| | |
| --- | --- |
| Capabilities catalogued | 1,093 across 25 domains |
| Already at parity | **362** |
| Open items after de-duplication | **735** (764 raw claims) |
| High impact | 142 · medium 314 · low 280 |
| Cost | easy 261 · moderate 344 · hard 87 · genuinely client-blocked 11 · out of scope 33 |
| State | none 495 · partial 203 · **MCP-only 37** · full 1 |
| High impact *and* easy | **55** |

The single most useful number is the last one. Fifty-five items are both high impact and small —
several are one-line capability declarations, and three of them are active defects rather than
missing features.

## How this was produced, and where to distrust it

Two fan-outs of subagents. The first catalogued Rider and VS per domain from primary sources, in
parallel with an inventory of our own LSP, DAP and MCP surfaces, then diffed each domain against
the repo with grep and Read. A completeness critic then attacked the result, which found a dead
inventory agent, 15 suspect findings and 12 whole categories nobody had covered; a second fan-out
fixed all three. Every gap row carries file-level evidence for the state it claims.

Known limits, stated so nobody over-reads the numbers:

- **De-duplication is approximate.** The same capability was often described in different words by
  agents working different domains. Clustering merged 26 of them; the measured duplicate rate in
  the named families was around 5%, so a handful of rows are still siblings. Treat "735" as
  ±5%, and never quote a count without saying which slice it covers.
- **Impact is a judgement, not a measurement.** It reflects how often a working C# developer would
  hit the gap, which is a claim about users we do not have telemetry on.
- **`out-of-scope` is a decision, not a fact.** IntelliTrace, Time Travel Debugging, the Snapshot
  Debugger, the T-SQL debugger and F# are tagged that way because of licensing, platform or "we are
  not writing a second language service", not because VS Code cannot express them.
- **`blocked-by-client` is used narrowly** — 11 rows out of 735. It means the LSP/DAP/VS Code host
  genuinely cannot express the thing. A webview, a custom `roslynSense/*` method or more analyzers
  are *work*, not blockers, and were retagged wherever an agent reached for the label to mean
  "hard".

## Five defects, not gaps

These are not missing features. They are code that is wrong today, found while checking claims, and
each was confirmed by reading the file.

**1 — Grouped code actions are offered and do nothing.** `CodeActionHandler.Flatten`
([CodeActionHandler.cs:153](../RoslynMCP/Lsp/Handlers/CodeActionHandler.cs#L153)) is called only
from `ConfigurationActionsAsync` (`:144`). The quick-fix loop (`:82`) and the refactoring loop
(`:101`) push the parent `CodeActionWithNestedActions` straight into the list; its
`GetOperationsAsync` yields nothing, so `TryResolveEditAsync` returns null and the lightbulb entry
visibly does nothing. This is every Introduce Variable / Field / Constant, every "generate into new
file", every multi-choice fix. A menu item that no-ops is indistinguishable from a broken install.
The fix is to hoist the existing `Flatten` call over both loops.

**2 — Code actions that add or delete files silently drop them. This destroys code.**
`TryResolveEditAsync` (`:191`) iterates `projectChange.GetChangedDocuments()` only —
`GetAddedDocuments()` and `GetRemovedDocuments()` are absent, and `WorkspaceEdit` carries only
`changes`, never `documentChanges` with `CreateFile`/`DeleteFile`. Move Type To Matching File
therefore applies the deletion from the source file, which *is* a changed document, and never
writes the destination. The correct handling already exists in
[RefactoringService.cs:170](../RoslynMCP/Services/Refactoring/RefactoringService.cs#L170) and `:185`
on the MCP path. Fix this first.

**3 — Multi-targeted projects resolve to one arbitrary TFM.** `CachedWorkspaceEntry.ProjectIds` is
a `Dictionary<string, ProjectId>` keyed by project path
([WorkspaceService.cs:1688](../RoslynMCP/Services/WorkspaceService.cs#L1688)) and `RefreshProjectIds`
(`:1694`) writes one entry per `Project`. MSBuildWorkspace emits one `Project` per target framework,
all sharing that path, so it is last-write-wins. Everything inside `#if NET8_0`-style regions then
gets diagnostics, completion and go-to-definition for whichever TFM won the race, with no way for
the user to tell or override. The code already knows: `:1195` comments that the same file can back
several `DocumentId`s.

**4 — Central Package Management silently disabled Updates and Consolidate.** *(Fixed.)*
`ProjectEvaluationService.ReadPackages` took `item.GetMetadataValue("Version")` off the evaluated
`PackageReference`. Under CPM the reference is version-less and the version arrives from restore
targets, so this yielded empty strings. Those flowed into the update path, where
`NuGetVersion.TryParse("")` fails and no update is ever reported, and into `ConsolidationsAsync`,
which saw one distinct empty version and flagged nothing. The panel painted blank versions. The
write path was always fine — it shells out to `dotnet add package`, which is CPM-aware.

`ReadPackages` now joins `PackageReference` to the evaluated `PackageVersion` items (`Include=` and
`Update=` both), honors `VersionOverride`, and skips the version-less `PackageReference` that
NuGet.targets projects each `GlobalPackageReference` into — which was the second, quieter half of
the same bug. No restore is needed, because `Directory.Packages.props` is imported through
`Microsoft.Common.props` and is already mtime-stamped for cache invalidation.
`RoslynMCP.Tests/Fixtures/CpmSolution` plus `ProjectEvaluationCpmTests` guard it.

**5 — Coverage decorations are wired to a property VS Code does not read.**
[testController.ts:635](../vscode-extension/src/testController.ts#L635) assigns detail through a cast:
`(coverage as { detailedCoverage?: ... }).detailedCoverage = detailed`. `vscode.FileCoverage` has no
such member; the sanctioned channel is `TestRunProfile.loadDetailedCoverage`, which appears nowhere
in `vscode-extension/src`. Per-file percentages show; the inline covered/uncovered decorations
receive nothing. The `StatementCoverage`/`BranchCoverage` construction above it is correct and can
be kept as-is.

## The question nobody had asked: does this run anywhere but Windows

It was not in the parity plan, not in the README, and not in any gap list until the critic demanded
it. The honest answer is that RoslynSense is Windows-shaped, and nothing tests otherwise.

- CI is `[ubuntu-latest, windows-latest]`, both x64. **macOS is never built or tested** — the 148
  test files have never run on Darwin, and `OperatingSystem.IsMacOS()` appears exactly once in the
  repo.
- **ARM64 does not work.** `DebuggerService.cs:567-569` hardcodes `netcoredbg-win64.zip` /
  `netcoredbg-osx-amd64.tar.gz` / `netcoredbg-linux-amd64.tar.gz` and selects by OS only.
  `RuntimeInformation.ProcessArchitecture` is never consulted, `DebugArch`
  ([ProcessArch.cs:8](../RoslynMCP.Debugger/ProcessArch.cs#L8)) models only x64 and x86, and
  `ProcessArch.OfExecutable` folds `Machine.Arm64` into `DebugArch.X64`. Apple Silicon and aarch64
  containers get a language server that may work and a debugger that certainly does not. Samsung
  ships both ARM64 assets; we do not ask for them.
- **The .NET Framework paths are unguarded on non-Windows.** `ProjectClassifier` decides
  `NetFramework` from the TFM string, not the host OS, so a `net48` project opened on Linux reports
  `isNetFramework: true` and `debugLaunch.ts:97-102` spawns `roslyn-sense --dap` into the ICorDebug
  backend. `IsWindows` / `SupportedOSPlatform` / `PlatformNotSupported` appear in none of the five
  files on that path. That violates the plan's own "degrade, don't fail" ground rule.
- **Case sensitivity is assumed away.** ~70 path comparisons and path-keyed dictionaries use
  `OrdinalIgnoreCase`. Worse, daemon identity is `solutionKey.ToLowerInvariant()`
  ([HostPaths.cs:50](../RoslynMCP/Host/HostPaths.cs#L50)), which drives the pipe name, the
  single-owner lock and the spawn mutex — so on ext4, `/src/App.sln` and `/src/app.sln` collide onto
  one daemon and the second exits with "Another host already owns …". A test asserts this behaviour
  deliberately, with a comment scoping the reasoning to Windows.
- **Nothing crosses a host boundary.** Every channel between MCP client, daemon and extension host
  is a named pipe or a `Path.GetTempPath()` file — `DaemonSpawner` (`:83`, `:99`),
  `DebugCommandPipeServer` (`:60`, `:223`), and six cross-process stores. There is no TCP option
  anywhere. Remote-SSH, Dev Containers, WSL and Codespaces are never mentioned in any file in the
  repository.
- **There is no way to install it remotely anyway.** The extension is never packaged or published
  in CI — the release job does `dotnet pack` and `dotnet nuget push` only — so no
  `devcontainer.json` can name it, and there is no server acquisition path beyond a toast telling
  the user to run `dotnet tool install -g`.

Rider ships Windows, macOS, Linux and Linux/ARM64 with a remote-development backend; VS Code plus
the C# extension is first-class in every remote mode. If the intended answer is "Windows only", say
so on line one of the README — it is a larger competitive fact than any individual feature in this
document. If it is not, the CI matrix and the ARM64 assets are the cheapest possible start.

## Root causes worth fixing before symptoms

Six items explain a disproportionate share of the 735.

| Root cause | What it takes down | Where |
| --- | --- | --- |
| No `codeActionKinds`, and `CodeActionContext.only` is never read | `editor.codeActionsOnSave` matches nothing, ever: no organize-imports-on-save, no fix-all-on-save, no cleanup-on-save, no kind-filtered "Refactor This" menu | `Protocol/Completion.cs:94-95`, `:110-111`; `LspServer.cs:130` |
| None of Roslyn's host option services are implemented (`IPickMembersService`, `IExtractInterfaceOptionsService`, `IChangeSignatureOptionsService`, …) | Every dialog-backed refactoring: Extract Interface/Class/Base Class, Pull Members Up, Change Signature, Move to Namespace, and the whole generate-with-picker family | needs an LSP-side picker protocol — a design decision, not a patch |
| Only C# and WebForms are served over LSP | XAML, MSBuild, `.editorconfig`, `.runsettings`, `appsettings.json` — and Razor, whose pack is MCP-only on purpose because the C# Dev Kit ships its own Razor server. Requests route by file extension, so `TextDocumentItem.LanguageId` is deserialized and still never read | `RoslynMCP/Languages/` holds the packs; one that implements no `ILanguage*Provider` reaches the editor with nothing |
| A block of capabilities is still MCP-only | Razor language services, all profiling and memory tooling, the database tools, designer regeneration, Change Signature — the server work is done and the editor cannot reach any of it. WebForms left this list when it became a language pack | `Languages/Razor/Tools/*`, `ProfileTool`, `MemoryTool`, `DatabaseTool`, `Services/Designers/` |
| Workspace eviction is far too coarse, and nothing is cached between daemon lifetimes | A branch switch or a single `.csproj` touch evicts every loaded project in every cached solution; every cold start pays `dotnet restore` plus a per-project design-time build with no `.vs`-equivalent to fall back on | `WatchedFilesHandler`, `WorkspaceService.EvictProjectAsync` |
| Nothing tells the user why the tool is wrong | No solution-load report, no reachable log, no per-project load-failure state, no "which MSBuild/SDK did I pick and why", no raw build output when a build fails without a `file(line,col)` diagnostic. `global.json` has zero occurrences repo-wide | `WorkspaceService.TryRegisterVisualStudioMSBuild:196-199` forces highest-version SDK and discards the locator's own ordering |

The `global.json` line deserves emphasis: wrong SDK means design-time builds fail, which means the
whole solution goes dark — no completion, no diagnostics, no navigation — with no explanation. The
fix is small. `Microsoft.Build.Locator` 1.11.2 already delegates SDK resolution to hostfxr and
accepts a `WorkingDirectory` query option; the work is plumbing the solution directory in and
deleting the `OrderByDescending(i => i.Version)`.

## Start here: high impact, small change

Fifteen of the 55 high-and-easy rows, ordered by value per hour.

1. **Emit `CreateFile`/`DeleteFile` document changes from resolved code actions.** Stops active data
   loss; closes Move Type To File, Extract Interface/Class/Base Class, Move Static Members and
   generate-into-new-type at once. The logic exists in `RefactoringService.cs:170-190`.
2. **Hoist `Flatten()` over the fix and refactoring loops.** One edit; turns every nested code
   action from a no-op into a working one.
3. **Map Roslyn's diagnostic tags to LSP `DiagnosticTag`.** `DiagnosticTag` appears zero times in
   the repo. Roslyn already sets `WellKnownDiagnosticTags.Unnecessary`. This is unused-code fading
   and deprecated strikethrough for a mapping — the highest visibility per line of code in the
   document.
4. **Declare `codeActionKinds`, honour `context.only`, implement `source.organizeImports` and
   `source.fixAll`.** Two record fields, one filter, one kind mapping — and it unlocks
   actions-on-save, organize-usings, and kind-filtered refactoring menus.
5. **Project `commitCharacters` onto completion items.** Roslyn's `CommitCharacterRules` already
   carries the data; the property is declared in `Protocol/Completion.cs:42` and never assigned.
   Typing `Console.Writ(` currently inserts `Writ(`.
6. **One `IsUserCode` predicate for the debugger** — does this module's PDB point inside the
   solution. Applied to frames and to stepping, it closes Just My Code, `[External Code]` collapse,
   stepping filters, and makes step-over-properties tractable.
7. **`[DebuggerDisplay]` support.** Ship display before proxy; it is the attribute the BCL and every
   well-written library actually use, and without it Locals is a raw field dump for
   `DateTimeOffset`, `Dictionary<,>`, `ImmutableArray` and every EF entity.
8. **Seven DAP capability declarations plus small handlers** in `DapServer.Capabilities()`
   (`:675-693`): `supportsFunctionBreakpoints`, `supportsCompletionsRequest`,
   `supportsClipboardContext`, `supportsValueFormattingOptions`, `supportsStepInTargetsRequest`,
   `supportsBreakpointLocationsRequest`, `supportTerminateDebuggee`. VS Code already has the UI for
   every one.
9. **Expand `exceptionBreakpointFilters` past the single `all` entry** (`:690`) and add per-filter
   conditions. VS Code renders the list and the condition editor for free.
10. **Fix the coverage decoration channel** — delete the cast, set `profile.loadDetailedCoverage`.
11. **Honour the client's `FormattingOptions`.** `FormattingHandler` ignores `p.Options` in all three
    entry points, so the server fights the user's `tabSize`/`insertSpaces`.
12. **Inactive `#if` region dimming.** Roslyn hands you the disabled-text spans off the syntax tree;
    publish them as a semantic token type or a decoration notification.
13. **`global.json` in SDK selection**, per the root-cause table above.
14. **Port the analyzer merge into `get_code_actions`.** The MCP tool
    (`CodeActionsTool.cs:91-105`) sees only compiler and syntax diagnostics at Error/Warning, so
    IDE0xxx never produces a fix for the AI. The LSP handler already does it correctly at
    `CodeActionHandler.cs:56-65` — it is a copy.
15. **Wire Fix All at document scope** via `WellKnownFixAllProviders.BatchFixer`. `FixAllProvider`
    appears nowhere. Without it, turning on one analyzer produces hundreds of warnings and no way to
    act on them — so people turn the analyzer back off, which quietly wastes the entire analyzer
    investment already made.

across the 25 domains are covered today, and a document that lists only holes will drive someone to

editor) / `full`. **Cost** is `easy` / `moderate` / `hard` / `blocked-by-client` (the protocol or
host genuinely cannot express it) / `out-of-scope` (a decision).
