# Database performance tuning

The `csharp-database` skill covers *capturing* evidence: `DbQuery` with `includeExecutionPlan: true`
to get a plan, `DbPlan` with `summary` / `warnings` / `operators` to read it. This skill covers what
to *do* with that evidence — and what to check when there is no single slow query, just a slow
database.

## Workflow

1. **Reproduce with the real query.** Tune the query the application sends, not a simplified
   version. Parameterised SQL through `parameters` measures differently from concatenated literals —
   the server caches and sniffs plans for the parameterised form. For EF, log the generated SQL
   rather than guessing at it.
2. **Capture a plan** — `DbQuery` with `includeExecutionPlan: true`, then `DbPlan`:
   - `warnings` first. Native warnings (implicit conversion, spill to tempdb, missing join
     predicate), missing-index suggestions, and estimate-vs-actual mismatches are usually the
     answer.
   - `operators` sorted by `actual_elapsed` to find where the time went. Estimated cost is the
     optimiser's model; actual elapsed is reality. When they disagree, trust elapsed.
   - Compare `actual_rows` against `estimate_rows` per operator. A large mismatch (100×+) means the
     optimiser was misled — stale statistics, parameter sniffing, or a construct it cannot estimate —
     and every downstream join and memory-grant decision inherits the error.
3. **Diagnose against the engine reference.** Read the file for the connection's provider — each
   maps plan shapes and predicate patterns to fixes, has an indexing playbook, and carries the
   monitoring queries for workload-level analysis:
   - `mssql` → [references/sql-server.md](references/sql-server.md)
   - `psql` → [references/postgres.md](references/postgres.md)

   When the query is generated by an ORM — EF Core, EF6, or LINQ to SQL — also read
   [references/linq.md](references/linq.md): the fix for what the plan shows is often in the
   C# that produced the SQL, not in the SQL.
4. **Fix the root cause, then re-measure** with the same `DbQuery` + plan capture. Report before and
   after — operator that dominated, rows read, elapsed — not just "it is faster now".

## The order of suspicion

Work cheapest-to-most-invasive. Each step frequently makes the later ones unnecessary:

1. **The predicate** — a non-sargable WHERE clause (function around a column, type mismatch,
   leading-wildcard LIKE) turns an index the table already has into dead weight. Rewriting the
   predicate is free; an index is not.
2. **The statistics** — if estimates and actuals diverge wildly, `UPDATE STATISTICS` may fix the
   plan without touching query or schema.
3. **The query shape** — N+1 loops, correlated subqueries in the SELECT list, `SELECT *` feeding a
   sort, DISTINCT papering over a fan-out join. These are C#-side or SQL-side rewrites.
4. **The index** — only after the above. Derive it from what the plan actually did (the reference
   shows how), not from a hunch, and weigh its write cost: every index is a tax on INSERT/UPDATE.
5. **Hints and forced plans** — last resort, and say so out loud. They freeze today's shape against
   tomorrow's data.

## The C# side of slow queries

Some of the most common database problems are created in the .NET code, not the SQL. The
highlights are below; [references/linq.md](references/linq.md) carries the full treatment —
per-ORM translation behavior (EF Core, EF6, LINQ to SQL), plan-cache pollution from `Contains`
and dynamic queries, tracking and materialization cost, and the write-path traps:

- **`string` parameters are NVARCHAR.** ADO.NET and EF send C# strings as `NVARCHAR` by default.
  Against a `VARCHAR` column the server converts *the column*, killing every index seek on it. The
  plan shows it as a `PlanAffectingConvert` warning. Fix in code: `SqlParameter` with an explicit
  `SqlDbType.VarChar`/size, EF `HasColumnType("varchar(...)")` or `.IsUnicode(false)`.
- **N+1 from lazy loading or per-item queries.** A loop issuing one query per element shows up
  server-side as a cheap plan executed thousands of times — no single capture looks slow. Batch it:
  `Include`/projection in EF, a joined query, or a TVP/temp-table join for large ID lists.
- **Large `IN` lists from `Contains(...)`.** Each distinct list length compiles a new plan and
  bloats the plan cache; past ~20 values a temp table or TVP join is faster and cacheable.
- **Unbounded result sets.** Queries returning everything so the application can filter in LINQ; add
  the predicate and pagination (with a deterministic tiebreaker column) to the SQL.
- **Long-lived transactions** spanning application work (HTTP calls, message handling) hold locks
  and inflate the version store. Keep the transaction around the database work only.

## Tool selection

| Task | Preferred Tool | Avoid |
|------|----------------|-------|
| Find where the time went in a slow query | **DbQuery** `includeExecutionPlan`, then **DbPlan** `operators` by `actual_elapsed` | Reasoning from the SQL text alone |
| Check for the usual culprits | **DbPlan** `warnings` | Reading raw plan XML by eye |
| Find what the whole workload spends time on | **DbQuery** against the DMVs in the reference | Tuning the first query someone mentions |
| Validate an index idea | Create it in a dev database, re-capture the plan | Recommending DDL nobody measured |
| Understand a deadlock | The deadlock XML (Extended Events `xml_deadlock_report`), patterns in the reference | Retry-loops that hide the cycle |

A plan is evidence about one execution against one data distribution. Say what the plan showed
alongside what you concluded from it, and flag when a dev-database measurement may not hold in
production.
